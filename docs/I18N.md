# i18n conventions

> Source of truth for behavior: `CLAUDE.md` §i18n and `docs/mindsetis-mvp-tz.md` §5.12.
> This file documents _how_ the pieces already in the repo fit together — it does not
> introduce new rules beyond what's in CLAUDE.md.

## Stack

- **next-intl** (`i18n/routing.ts`, `i18n/navigation.ts`, `i18n/request.ts`), App Router
  `[locale]` segment routing, wired via `next.config.ts` and `middleware.ts`.
- Locales: `en` (default, source of truth) and `es` (readiness). Add new locales only in
  `i18n/routing.ts` (`routing.locales`) — never hardcode a locale list elsewhere.

## English-first (MUST)

- `messages/en.json` is the **source** — every user-facing string is authored there first,
  with real English copy.
- `messages/es.json` mirrors the same key structure (added via the `add-i18n-keys` skill),
  translated to Spanish. If no translation exists yet, the key still exists (English
  fallback / `TODO`) so the two files never drift structurally.
- **No auto-detection, no cookie-based routing.** `i18n/routing.ts` sets
  `localeDetection: false`: the middleware never infers a locale from the browser's
  `Accept-Language` header, and it never reads the `NEXT_LOCALE` cookie to pick a locale
  either — a bare/rootless path (no `/en` or `/es` prefix) always resolves to
  `defaultLocale` (`en`), regardless of any cookie value. This is intentional
  (English-first): every visitor lands on English by default unless the URL itself already
  says otherwise.
- The locale choice persists purely through the URL, not the cookie. `localePrefix:
'always'` keeps the locale segment in every path (`/en/...`, `/es/...`), and all internal
  navigation goes through `@/i18n/navigation` (`Link`, `redirect`, `usePathname`,
  `useRouter`, `getPathname`), which carries the current locale forward automatically. The
  `LocaleSwitcher` (`components/i18n/LocaleSwitcher.tsx`, wired into
  `components/layout/Header.tsx`) is the only way the locale changes: picking a language
  replaces the current path under the new locale prefix (e.g. `/en/foo` → `/es/foo`).

## Using translations in code

- **RSC** (Server Components, Server Actions rendering markup): `getTranslations` from
  `next-intl/server`.
- **Client Components**: `useTranslations` from `next-intl`.
- **Navigation**: always import `Link`, `redirect`, `usePathname`, `useRouter`,
  `getPathname` from `@/i18n/navigation` (wraps `next/link` / `next/navigation` with the
  locale-aware equivalents) instead of the plain Next.js APIs, anywhere under
  `app/[locale]/**` or in shared components.
- **No hardcoded UI strings.** Every visible string is a translation key. Add keys via the
  `add-i18n-keys` skill, namespaced by feature/component
  (e.g. `booking.title`, `localeSwitcher.label`), sorted, and kept in the same order in
  both `en.json` and `es.json`.

## Profile / author content is exempt

User-authored profile content (bios, session descriptions, event copy, etc.) is stored in
the author's own `content_locale` (`profiles.content_locale`, default `'en'`) and is
**never** run through the UI dictionaries above and **never** auto-translated in storage —
translating it would put us in the business of rewriting what a Mindsetter or Member
actually wrote. The only place profile content gets translated at all is client-side, at
render time, via the Google Translate widget (styled for the dark theme) — it translates
the rendered page in the visitor's browser and never touches the database. UI chrome
(nav, buttons, form labels, system messages) always goes through next-intl regardless of
which locale a given profile's content happens to be in.

## Verifying changes

```bash
# both message files must be valid JSON and structurally identical
node -e "JSON.parse(require('fs').readFileSync('messages/en.json'))" \
  && node -e "JSON.parse(require('fs').readFileSync('messages/es.json'))"
```

Run `npm run typecheck` and `npm run lint` after touching anything under `i18n/`,
`components/i18n/`, or `messages/*.json`.
